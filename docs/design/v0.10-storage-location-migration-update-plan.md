## 1. 功能本质与本次更新目标

### 1.1 存储位置迁移到底解决什么问题

存储位置迁移的产品目的，是让用户把 N.E.K.O 的可变用户数据运行根从当前目录迁移到另一个目录，并让下一代运行时真正以新根初始化。它不是单纯的目录复制，也不是只改一个配置路径：

```text
用户选择新运行根
  -> 预检源/目标/数据边界
  -> 持久化迁移意图与恢复信息
  -> 旧服务停止写入并退出
  -> 下一代 launcher 在服务初始化前复制和校验
  -> 提交新的运行根
  -> 以新根启动 Main / Memory / 插件运行时
  -> 源目录保留，用户可稍后清理
```

这样设计的原因是 `ConfigManager`、Main Server、Memory Server 和插件运行时在启动时就会绑定目录。运行中热切换会产生新旧目录同时写入、配置分叉和 cloudsave/state 错配，因此不作为本次方案目标。

### 1.2 0.10 的目标

1. 用户发起迁移后，无论后端是否已经退出、launcher 是否接力成功，页面和桌面端都必须在有界时间内进入“完成、可恢复或可退出”之一，不能永久卡在维护页。
2. 迁移本身必须有可追踪的 operation、launcher generation 和最后心跳，能够区分“正在复制”“后端尚未启动”“launcher 接力失败”和“页面只是没有刷新”。
3. 迁移对象必须从产品语义和代码实际写入点重新核对，解决运行时目录、诊断清单、legacy import、清理逻辑之间的遗漏和不一致。
4. 失败、强退、进程崩溃和下一次启动必须保持可恢复：不误提交目标、不删除源、不丢失 checkpoint。
5. NEKO-PC 负责宿主保护、窗口和后端代际观测；不在 Electron 主进程复制数据或自行决定迁移策略。

### 1.3 非目标

- 不做运行中无重启热切换。
- 不自动删除迁移源。
- 不把 cloudsave、`state/`、`.cloudsave_staging/`、`cloudsave_backups/` 从 anchor 搬到用户运行根。
- 不让前端或 NEKO-PC 直接写 `storage_policy.json`、`storage_migration.json`、`root_state.json`。
- 不因为历史 commit 或旧方案曾出现过，就重新引入 `publishing`、逐文件 SHA-256 全事务、community private-state 专用迁移或其他已移除 machinery。
- 不把“进度百分比”作为事务提交条件；提交仍由复制、校验、策略和 root state 的后端事务决定。

## 2. 当前代码作为方案约束

以下是设计方案必须尊重的事实，不是本方案要重复实现的现状文档。

| 事实 | 当前代码证据 | 对 0.10 的约束 |
| --- | --- | --- |
| 当前迁移清单只有 11 项 | `utils/storage/migration.py:61-73` 的 `MIGRATED_RUNTIME_ENTRY_NAMES` | 扩展清单必须做完整性审计，不能直接把所有 ConfigManager 属性自动加入 |
| anchor 固定保存状态和 cloudsave | `utils/config_manager/storage_roots.py` 的 `local_state_dir`、`cloudsave_dir`、staging/backups 属性 | policy、migration、root state、cloudsave 继续固定在 anchor |

| 正常迁移失败会返回 `attempted=True` 并保留源/检查点 | `utils/storage/migration.py:401-457,604-609` | 继续保持幂等和源数据安全；补的是外围接力失败 |

| Web maintenance poll 无限循环 | `static/app/app-storage-location.js:1488-1575` | 增加有界等待和恢复终态 |

| PC `backend_unreachable` 只会继续轮询 | `src/main/storage-gate.js:195-239,826-855` | 增加宿主 watchdog 和本地退出动作 |
| PC 已有本地退出 IPC | `src/main/storage-gate.js:1055-1074` | 复用 `neko:host:close-window`，不新增绕过状态文件的后端写入 |

### 2.1 当前迁移对象的重新核对结果

当前实际复制清单为：

```text
config, memory, plugins, live2d, vrm, mmd,
workshop, character_cards, card_faces, jukebox, avatar_tools
```

当前必须固定留在 anchor 的内容为：

```text
state/, cloudsave/, .cloudsave_staging/, cloudsave_backups/
```

当前 `ConfigManager` 还定义了 `pngtuber_dir`、`project_config_dir`、`project_memory_dir` 等路径。它们不能仅因为“存在目录属性”就自动迁移，也不能仅因为不在 11 项清单里就默认为不重要。0.10 要先完成目录所有权审计，再形成明确的纳入/排除决策：

- `pngtuber/`：建议纳入用户运行时迁移候选，因为代码把用户 PNGTuber 文件写入 `selected_root/pngtuber`；在产品确认前，先作为“待决策的已知缺口”，不得静默复制。
- `card_faces/`：当前已复制，但诊断/清单/测试必须补齐，避免“迁移了但无法观测”。
- `project_config_dir`、`project_memory_dir`：维持项目级数据的独立语义，不因本次运行根迁移自动跟随，除非另有项目数据迁移方案。
- Steam Workshop 实际安装目录、外部绝对路径：不复制；只迁移运行时目录内的配置，并通过路径重写处理已知绑定。
- legacy import 清单：继续作为独立的升级导入链核对，不直接等同于主动迁移清单。

目录清单的最终权威应从“字符串元组”升级为带元数据的迁移注册表，至少描述：运行时相对路径、是否用户数据、是否 anchor 固定、是否可重写路径、是否参与诊断、是否参与 retained cleanup、legacy import 是否同源。这样新增目录时不会只漏改一个列表。

### 2.2 本方案实际覆盖的入口

方案不把所有带有 `storage` 字样的文件都算成用户入口，只覆盖下面这些实际触点：

| 入口/接续点 | 当前代码 | 0.10 要改变的内容 |
| --- | --- | --- |
| 主页面启动选择与维护 | `templates/index.html`、`static/app/app.js`、`static/app/app-storage-location.js` | 启动 barrier、维护超时、恢复/退出终态 |
| Memory Browser 常驻管理 | `templates/memory_browser.html`、`static/js/memory_browser.js` | 复用同一 operation，避免重复提交，显示同一恢复状态 |
| 后端存储路由 | `main_routers/storage_location_router.py` | checkpoint、诊断、关闭和恢复合同 |
| launcher 接力 | `launcher_core/runtime.py` | 迁移失败/接力失败可消费，发布 generation/heartbeat |
| PC Pet/StorageGate | `N.E.K.O.-PC/src/main/storage-gate.js`、`src/main/backend-runtime.js` | watchdog、事件接收、窗口保护终态和本地退出 |
| PC preload/宿主桥 | `N.E.K.O.-PC/src/preload/shared/common.js` 及相关 bridge | 只增加诊断/状态通知能力，不开放状态文件写入 |
| legacy bootstrap import | `utils/cloudsave_runtime/legacy_migration.py` | 只做清单一致性核对，不与主动迁移合并 |

因此，主页面和 Memory Browser 是用户发起迁移的 Web 入口；PC 是宿主保护/退出入口；后端路由和 launcher 是内部事务接续入口。后续实现和验收必须按这些边界分工，不能让某一层代替另一层写状态。

## 3. 目标功能链路

### 3.1 正常迁移

1. 用户从主页面启动选择层或 Memory Browser 存储位置入口选择目标目录。
2. 后端执行只读预检：规范化路径、源/目标嵌套、权限、空间、目标现有内容、迁移注册表和外部目录警告。
3. 用户确认后，`/restart` 在 mutation lock 和 root-state transaction 内保存：
   - 稳定 operation id（复用现有 `txid`，不再另造同义 ID）；
   - 源根、目标根、选择来源和目标确认；
   - 旧 root state / migration 的回滚前像；
   - `maintenance_readonly` 和 `restart_pending:<target>`。
4. 受控关闭成功接受后，旧服务不得再回滚已经提交的 pending checkpoint。
5. launcher 启动时消费 checkpoint，在服务初始化前完成 preflight、copy、rewrite、verify、commit 和 retained source 记录。
6. launcher 发布包含 operation id 和 generation 的接力事件，释放旧代 ownership，启动下一代或交给明确的 owner relaunch。
7. 新代发出 `startup_begin`、`port_plan`、`startup_ready`；Web/PC 只在新代 ready 且 storage barrier 解除后恢复业务窗口。
8. 完成卡显示新根和 retained source。源目录继续保留，清理必须由用户显式操作。

### 3.2 后端失联或 launcher 没有接力

1. Web/PC 记录最后一次成功响应、最后一个 launcher 事件、operation id、generation、阶段和失败时长。
2. 在配置的等待预算内继续探测；有心跳则显示“迁移仍在进行”，无心跳且服务不可达则显示“正在等待后端接力”。
3. 超过预算后进入本地派生的 `backend_unreachable` / `handoff_timeout` 终态，提供：
   - 重新探测；
   - 查看诊断；
   - 安全退出应用；
   - 在可达时请求后端恢复/重试。
4. 本地退出只关闭桌面宿主，不清理 checkpoint、不提交目标、不删除源。用户下次启动时，launcher 继续消费 anchor 上的 checkpoint。
5. 后端恢复后，必须再次以 `/status` 的 ready 和 operation/generation 匹配为准，不能仅凭前端计时器判定成功。

### 3.3 迁移执行失败

1. 迁移引擎失败：继续写 `failed`、错误码、源根和恢复 root state；返回 `attempted=True`。
2. launcher 外围失败：必须将“存在 pending 但 runner 未完成”转化为可消费的失败/恢复结果；不能转成 `attempted=False` 后静默释放 ownership。
3. 下一代或明确的恢复代必须能够启动并展示失败原因；若无法启动下一代，至少保留 checkpoint 并由宿主进入可退出的恢复终态。
4. policy 只能指向确认可用的源根或恢复根；目标半成品不得成为稳定 selected root。

### 3.4 `rebind_only`

恢复中的原 selected root 重新可用时，继续使用 `rebind_only`：

- 不复制目录；
- 删除/替换的是恢复用的迁移意图，不是用户数据；
- 按现有 root state 事务提交原路径；
- 仍然经过新一代启动接力和 ready 验证；
- 不把 anchor fallback 误写成新的稳定运行根。

## 4. 目标状态和跨进程合同

### 4.1 不新增第二套持久化真源

仍然只保留三份后端权威状态：

- `storage_policy.json`：已经提交的长期运行根；
- `storage_migration.json`：当前迁移事务和恢复信息；
- `root_state.json`：当前 root mode、最后可用根和写入屏障。

`backend_unreachable`、`handoff_timeout` 是 Web/NEKO-PC 在后端不可达时派生的本地终态，不直接写进后端 canonical lifecycle。否则前端会在后端离线时制造另一份状态，下一次启动无法判断谁是权威。

### 4.2 `storage_migration.json` 建议新增字段

字段新增必须向后兼容：旧 checkpoint 缺字段时按空值/未知处理，不因为解析旧版本而删除迁移状态。

| 字段 | 用途 | 写入者 |
| --- | --- | --- |
| `txid` | 现有稳定 operation id，贯穿 Web、launcher、PC | `/restart` 创建时生成并沿用 |
| `launcher_generation` | 当前消费 checkpoint 的 launcher 代际 | launcher |
| `last_heartbeat_at` | 最近一次复制/校验/接力进展 | launcher |
| `current_entry` | 当前迁移注册表条目 | launcher |
| `entries_total` / `entries_done` | 条目级进度 | launcher |
| `bytes_total` / `bytes_done` | 可计算时的字节级进度 | launcher |
| `last_launcher_event` | 最近事件名称及时间 | launcher |
| `handoff_state` | `not_started`、`old_exiting`、`replacement_starting`、`ready`、`failed` | launcher |
| `handoff_error_code` | 接力失败的机器可读原因 | launcher |

`last_heartbeat_at` 和进度字段只用于诊断和显示；任何字段写失败都不能让目标策略提前提交，也不能删除源。

### 4.3 launcher 事件合同

沿用 `NEKO_EVENT`，不再让 PC 依赖兼容但当前不会发出的事件。建议事件为：

```text
storage_migration_processing
storage_migration_progress
storage_migration_restart
storage_migration_handoff_failed
startup_begin
port_plan
startup_ready
startup_failure
```

每个迁移事件至少携带：

```json
{
  "txid": "...",
  "launcher_generation": "...",
  "stage": "copying|verifying|handoff|ready|failed",
  "last_heartbeat_at": "...",
  "error_code": "..."
}
```

PC 必须按 `sourceProcess + txid + launcher_generation` 过滤旧事件；Web 通过后端 status 和宿主事件合并显示，但 `/status.ready` 仍是最终成功条件。

## 5. NEKO 后端更新方案

### 5.1 迁移注册表和数据覆盖完整性

涉及文件：

- `utils/config_manager/storage_roots.py`
- `utils/storage/migration.py`
- `utils/cloudsave_runtime/legacy_migration.py`
- `utils/storage/location_bootstrap.py`
- `main_routers/storage_location_router.py`
- `utils/storage/path_rewrite.py`

实施内容：

1. 将当前 11 项清单改为带元数据的唯一注册表，并由迁移、预检、diagnostics、retained cleanup、测试共同消费。
2. 对 `pngtuber/` 做产品决策：推荐纳入用户运行根迁移；若决定排除，必须在 UI、诊断、完成提示和文档中明确“仍留在旧根”，不能让用户以为所有用户数据都已迁移。
3. 将 `card_faces/` 补入 diagnostics、容量统计、进度和测试闭环。
4. 明确 project 级目录、external Workshop、anchor 固定目录的所有权，防止注册表把它们误复制。
5. 路径重写从单个 `workshop_config.json` 的特例扩展为注册表支持的规则，但只处理明确声明的运行根绑定路径；不能对未知字符串做全局替换。

完成标准：新增或删除一个运行时目录时，代码评审能从一份注册表看出复制、预检、诊断、清理、legacy import 和测试是否同步更新。

### 5.2 真实进度与心跳

涉及文件：`utils/storage/migration.py`、`main_routers/storage_location_router.py`、`utils/storage/location_bootstrap.py`。

实施内容：

- 预先统计注册表条目和可访问文件大小；无法统计时标记 unknown，不伪造百分比；
- 每完成一个文件或受节流保护的字节窗口更新 `last_heartbeat_at`、当前条目和计数；
- `GET /status`、`GET /bootstrap`、`GET /diagnostics` 透传最近心跳、进度和最后错误；
- 状态写入失败只记录日志并继续事务，不因“进度展示失败”破坏迁移；
- 进程重启后从 checkpoint 恢复“最后已确认条目”，不把中间复制结果直接当作已提交；
- 仍保持源保留、目标校验和策略最后提交的顺序。

### 5.3 `/restart`、`/exit` 和恢复语义

涉及文件：`main_routers/storage_location_router.py`、`utils/root_state_lock.py`、Main/Memory startup barrier。

实施内容：

1. `/restart` 返回 `txid`、目标、当前 stage 和 handoff 等待预算，便于页面和 PC 绑定同一操作。
2. 受控关闭尚未接受时，保留当前已有的精确回滚；关闭已接受后不因 HTTP 请求取消而回滚 checkpoint。
3. `/exit` 仍只负责后端可达时的受控关闭；后端不可达时不虚报成功，由 Web/PC 走本地退出兜底。
4. `GET` 诊断接口继续只读；不得为了报告 heartbeat 在轮询里偷偷改变 root mode。
5. Main/Memory barrier 继续由后端统一控制；本地退出不释放 barrier，也不清理状态。

### 5.4 launcher 接力修复

涉及文件：`launcher_core/runtime.py`。

#### 必须修复

- `_resolve_storage_layout_for_launch()` 捕获迁移执行外围异常时，不再无条件返回 `attempted=False`；应读取 pending checkpoint，生成包含 `txid`、error code、`restart_intent` 的失败结果。
- `_maybe_schedule_storage_restart()` 对“迁移已尝试但失败”“pending 存在但 runner 外围异常”“rebind_only”分别建立明确的 restart reason，并发出可消费事件。
- `_spawn_restarted_launcher()` 抛出异常时，必须写入 handoff failure、保留 checkpoint，并让宿主得到 `storage_migration_handoff_failed`；不能只在 finally 打 Warning 后释放 ownership。
- 下一次 launcher 启动必须能按 checkpoint 幂等判断：继续未完成事务、显示失败等待用户、或安全回源；不能重复复制造成新的策略提交。

#### 不改变

- 不让 launcher 在目标未校验成功前保存 selected policy。
- 不让旧代和新代同时成为可写 owner。
- 不把 self-spawn 变成 PC 的隐式职责；owner-driven relaunch 如果启用，必须保留现有 lease、Job Object 和 parent-death 约束。

## 6. NEKO-PC 更新方案

### 6.1 StorageGate 本地状态机

涉及文件：`N.E.K.O.-PC/src/main/storage-gate.js`。

当前 `backend_unreachable` 只是快照值。目标状态机应增加本地计时和终态：

```text
checking / maintenance
  -> backend_unreachable (连续失败，仍在预算内)
  -> handoff_timeout (预算耗尽，等待下一次用户动作)
  -> ready (收到匹配代际的 ready)
  -> recovery_required (后端返回失败/恢复态)
```

要求：

- storage/status 和 system/status 的失败分别记录，不用一次失败判定后端死亡；
- 采用两个预算：短期接力等待、较长迁移等待；均可配置，测试可注入；
- `handoff_timeout` 只停止无限轮询并显示动作，不删除 checkpoint；点击 Retry 可重新开始探测；
- 本地退出按钮直接复用 `neko:host:close-window`/`requestAppQuit`，不依赖后端 `/exit`；
- 只有匹配当前 operation/generation 的 `startup_ready` 或可验证的 `/status.ready` 才退出 maintenance protection；
- 卫星窗口在 ready 前继续隐藏，退出应用时不恢复卫星窗口。

### 6.2 backend-runtime 代际观测

涉及文件：`N.E.K.O.-PC/src/main/backend-runtime.js`。

实施内容：

1. 保存当前 storage operation、last event、旧 launcher exit code、backend pid、currentLaunchId 和 active ports。
2. 把已有的 `startup_begin`、`port_plan`、`startup_ready`、`startup_failure` 与迁移事件关联起来；丢弃旧 sourceProcess/launch id 事件。
3. `storage_migration_restart` 不只更新 loading 文案，还要启动 bounded handoff watchdog；它不负责复制数据，也不重复启动已有 owner。
4. 超时或 spawn/relaunch 失败时，向 StorageGate/Web 发出本地 `handoff_timeout`/`recovery_required` 事件，并保留诊断。
5. 继续支持旧 launcher 事件解析，但测试必须区分“兼容解析”与“当前 NEKO launcher 实际会发出的事件”。

关键实现约束：`src/main.js` 启动完成后会关闭 loading window；因此当前 `backend-runtime.js:1140-1181` 仅调用 `updateLoadingWindowStatus()` 不能让已经显示的 Pet 页面收到迁移事件。新的 processing/progress/restart/timeout 状态必须通过主进程到 preload/Web 的 IPC 或等价宿主事件桥推送，不能继续把已销毁的 loading window 当作用户可见通道。

### 6.3 preload 与宿主能力

涉及文件：`N.E.K.O.-PC/src/preload/shared/common.js`、相关 bridge、`storage-gate.js`。

当前已有 `pickDirectory`、`openPath`、`closeWindow`。0.10 可新增只读诊断订阅或一次性查询桥，例如 `getStorageMigrationDiagnostics`、`onStorageMigrationStatus`，但不提供写 policy/checkpoint 的 bridge。若实现复杂度过高，优先保留 Web `/diagnostics`，确保本地退出仍独立可用。

### 6.4 置顶问题的正确处理

always-on-top 和全屏 overlay 是症状放大器，不是迁移根因。方案只做两件事：

- 维护遮罩仍保持可交互；
- `/exit` 失败、后端不可达或 handoff timeout 时，允许本地 host close 关闭应用。

不把“取消置顶”作为根治，也不在窗口关闭时清理迁移状态。

## 7. Web 与 Memory Browser 更新方案

### 7.1 关闭语义

涉及文件：`static/app/app-storage-location.js`、`static/js/memory_browser.js`、现有 frontend tests。

当前 `requestHostWindowClose()` 在 `/exit` 失败时直接返回，而同文件已有 `closeHostWindowOnly()`。目标行为：

1. 先尝试 `/exit`，设置短超时，给后端一次受控退出机会。
2. 如果响应失败、超时或后端不可达，显示“服务已断开，迁移检查点会保留”的确认。
3. 用户确认后，无条件调用 `nekoHost.closeWindow()`；没有宿主桥时再尝试 `window.close()`。
4. 用户取消则回到维护页，可 Retry 或查看诊断。

现有 `tests/frontend/test_storage_location_startup.py` 中“关闭请求失败后保持窗口、不调用 host close”的断言必须改为新契约，并增加超时而非只有 HTTP 503 的用例。

### 7.2 有界维护页

涉及文件：`static/app/app-storage-location.js`。

把现在的无限 `while (state.phase === 'maintenance')` 改为：

- 记录 `maintenanceStartedAt`、`lastSuccessfulPollAt`、`lastHeartbeatAt`、`failureCount`；
- status 可达且 heartbeat 前进：显示复制/校验阶段和真实进度；
- status 可达但 heartbeat 未前进：显示“仍在处理，最近心跳时间”，不立即判死；
- storage/status 与 system/status 都失败：进入本地 `backend_unreachable`，达到预算后 `handoff_timeout`；
- 终态显示 Retry、Diagnostics、Exit；不显示“请不要关闭当前页面”这种唯一动作；
- 重新探测成功后恢复原维护状态；ready 且 operation/generation 匹配后 reload；
- `window.location.reload()` 仍只由 ready 触发。

建议默认值只作为可测试配置，不在文档中把某个秒数写成不可变协议：例如接力短等待、迁移总等待、重试间隔应可由测试注入并按平台调整。

### 7.3 进度和文案

- 阶段名称、当前条目、条目数、字节数和最近心跳来自后端/launcher 证据；
- 不再用固定百分比暗示复制已完成；无法统计时显示阶段和心跳，不伪造数字；
- 失败页面展示错误码对应的可理解文案和 operation id，详细异常只进日志/诊断；
- Memory Browser 从管理 modal 进入维护后，使用同一 operation id 和同一终态，不重复创建第二次迁移。

## 8. 数据安全、幂等和回滚要求

### 8.1 任何阶段都必须成立

- 原 selected policy 不在目标校验前提交。
- 源数据在用户明确清理前保留。
- 半成品目标不能被当成 stable current root。
- 本地退出不修改三份后端权威状态。
- 轮询、事件重复、launcher 重启不会创建第二个 operation 或重复提交策略。
- 旧代 shutdown 已接受后，不能因客户端取消把已提交的 pending checkpoint 删除。

### 8.2 下次启动决策

| 启动时发现 | 下一步 |
| --- | --- |
| `pending/preflight/copying/verifying/committing` 且源可用 | launcher 按 operation 继续或安全回滚，不启动普通业务 |
| `failed` 且源可用 | 进入恢复 UI，允许回源、重试或重新选择；不自动把目标设为当前 |
| `completed` 且新根可用 | 以 policy 启动，完成卡可处理 retained source |
| `maintenance_readonly` 但无可消费 checkpoint | 进入诊断/恢复，不静默放行普通写入 |
| `rebind_only` | 只重绑定原 selected root，不复制运行时目录 |

### 8.3 恢复动作的边界

恢复按钮只能请求后端或重新启动 launcher。前端和 PC 不直接删除 checkpoint、改 policy、改 root state；只有后端在锁和事务边界内做这些动作。

## 9. 分阶段交付

### P0：先保证用户不会被困

交付内容：


- Web `/exit` 失败后仍可本地关闭；
- Web maintenance watchdog 和恢复/退出终态；
- PC `backend_unreachable` watchdog 和本地退出；
- launcher 外围异常不再静默 `attempted=False`；
- 新增故障注入测试：后端 503、ECONNREFUSED、请求超时、launcher migration runner 抛异常、spawn replacement 失败。

P0 完成后，用户即使看不到后端，也能安全退出；下次启动仍能消费或恢复 checkpoint。

### P1：补齐跨进程接力和迁移对象合同

交付内容：

- `txid`/generation/heartbeat 贯穿 checkpoint、launcher event、PC runtime 和 Web；
- `storage_migration_processing/progress/handoff_failed` 成为当前真实事件，而不是 PC 的死兼容分支；
- 迁移注册表覆盖预检、diagnostics、cleanup、legacy import 和测试；
- 明确 `pngtuber` 是否纳入，并处理 `card_faces` 诊断缺口；
- PC/launcher 对旧代事件、重复事件和新代 ready 的关联测试。

### P2：提升长任务体验和校验能力

交付内容：

- 文件/字节级进度和节流心跳；
- 大目录、外置盘、同步目录的速度与剩余时间诊断；
- 在有明确性能预算后，再评估更强校验（例如选择性哈希）；
- 不在 P2 之前引入 publishing 全事务或自动删除源。

## 11. 诊断、发布与回滚

### 11.1 必须可回答的问题

任何“迁移卡住”报告都必须能回答：

1. operation/txid 是什么？
2. 最后一次后端 heartbeat 是什么时候？
3. 最后一个 launcher event 是什么、来自哪一代、哪个 sourceProcess？
4. 旧 launcher 是否退出、退出码是什么？
5. replacement 是否 spawn、是否发出 `startup_begin`/`port_plan`/`startup_ready`？
6. 当前 selected/effective/anchor root 分别是什么？
7. migration/root_state/policy 是否仍在安全的 pending/failed/recovery 状态？

### 11.2 发布顺序

1. 先发布 P0 后端/前端/PC 兜底，使旧 checkpoint 可安全退出。
2. 再发布 P1 事件和注册表合同；新增字段必须兼容旧 checkpoint。
3. 最后发布 P2 进度和性能增强。
4. 每阶段都保留旧字段解析和源数据保留策略，禁止同一版本同时改变 checkpoint 语义和删除策略。

### 11.3 回滚

- 代码回滚不能删除用户的 `storage_migration.json`、`storage_policy.json` 或 `root_state.json`。
- 新字段必须可被旧版本忽略；若旧版本无法消费新状态，发布前必须提供兼容降级或阻止回滚启动的明确提示。
- 任何失败都优先回到源根/恢复根，不自动清理目标或 source。

## 12. 明确不做与待决策项

### 不做

- Electron 主进程复制用户数据；
- PC 直接修改后端迁移状态；
- 维护页无限等待；
- `/exit` 失败后把用户锁在置顶页面；
- 自动删除源；
- 把兼容事件 case 当作真实进度来源；
- 把历史 `entries.py` 扩展清单、private state、publishing、SHA-256 全事务直接恢复。

### 必须在实施前定案

1. `pngtuber/` 是否纳入用户运行根迁移；
2. 接力等待预算的默认值和平台差异；
3. `handoff_timeout` 是仅本地 UI 状态，还是需要后端持久化诊断字段；
4. owner-driven relaunch 是否在 NEKO-PC 当前发布模式启用；
5. 长任务是否需要字节级统计，以及统计成本是否可接受；
6. 更强内容校验是否只用于用户选择的高风险场景，而不是所有迁移默认启用。

## 13. 完成定义

0.10 存储迁移更新只有同时满足以下条件才算完成：

- 用户数据迁移对象经过逐项核对，纳入/排除有产品和代码证据；
- 正常迁移、rebind、失败、强退、后端失联、launcher 接力失败都有确定终态；
- `/exit` 失败不会再把用户锁在置顶维护页；
- 下一次启动可以消费或恢复 checkpoint，源数据未被误删；
- launcher、Web、NEKO-PC 使用同一 operation/generation 观测迁移接力；
- progress/heartbeat 能说明“慢”还是“无进展”，但不改变提交安全条件；
- Main/Memory barrier、policy、migration、root state 的职责仍然分离；
- 自动化、跨仓库契约和发布态故障注入通过；
- 文档中的“当前实现”和“待实施方案”不再混写。
