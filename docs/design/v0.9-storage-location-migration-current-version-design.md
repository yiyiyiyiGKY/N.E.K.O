> 文档状态：当前代码基线（Current Implementation Baseline）
>
> 核对日期：2026-09-24
>
> 适用仓库：`N.E.K.O`、`N.E.K.O.-PC`
>
> 版本证据：`N.E.K.O/config/application.py:22` 与 `N.E.K.O.-PC/package.json:4` 均为 `0.9.0`。

本文重新按当前两个仓库的实际代码整理。它不是把第一版文档换一个标题，也不是把未来修复方案伪装成现有功能，而是回答四个问题：

1. 第一版存储位置迁移之后，实际增加了哪些功能；
2. 这些功能在 0.9.0 中哪些仍然生效，哪些已经被后续重构移除；
3. 用户从打开应用到迁移完成、失败或恢复，当前真实调用链是什么；
4. 当前实现明确不包含什么，以及后续维护应按什么顺序进行。

事实优先级：当前代码和可复现测试 > 当前调用方 > Git 历史中的实现 > 设计文档。历史 commit 只用于解释演进，不能证明当前功能仍存在。

## 1. 先给结论：0.9.0 实际是什么

0.9.0 的存储位置功能由三个相互配合、但不能混为一谈的部分组成：

1. **启动位置选择与恢复**：应用启动时判断是否需要首次选择、是否存在已提交但暂时不可用的自定义根、是否存在未完成迁移，并在后端启动屏障下提供受限 UI。
2. **用户主动迁移**：用户选择不同运行根后，后端持久化 pending checkpoint 和 `maintenance_readonly`，关闭旧服务；launcher 在新服务初始化前复制、统计校验、提交策略并拉起下一代服务。
3. **桌面宿主协作**：NEKO-PC 负责原生目录选择、打开目录、维护期间卫星窗口保护、Pet 遮罩交互、后端代际端口接收和本地退出；它不负责复制数据，也不决定迁移策略。

当前真正迁移的运行时目录只有：

```text
config
memory
plugins
live2d
vrm
mmd
workshop
character_cards
card_faces
jukebox
avatar_tools
```

当前明确不在主动迁移清单中的包括：`pngtuber`、anchor 固定的 `state/`、`cloudsave/`、`.cloudsave_staging/`、`cloudsave_backups/`、项目源码侧的 config/memory、日志和其他根目录散落内容。`workshop_config.json` 只做已知运行根路径重写，Steam Workshop 外部安装目录不由本功能复制。

当前代码没有实现或不应写成现状的内容：逐文件 SHA-256 迁移证明、`publishing` 阶段、完整扩展运行时清单、社区私有状态专用迁移、Electron 主进程直接执行迁移、自动删除源目录。

当前已确认的用户侧缺陷仍存在：维护页后端失联时无限等待，且 Web 关闭按钮在 `/exit` 失败时不走本地关闭 IPC。这是维护项，不改变上面已经存在的迁移主链路。

- 与 storage-location 主迁移无关的社区私有状态专用迁移流程；

## 3. 功能边界：什么纳入，什么排除

### 3.0 当前代码中的真实入口与接续点

这里的“入口”按用户能触发、页面能进入、或下一代进程必须接手的实际代码点列出；不是把所有包含 `storage` 字样的文件都算成迁移入口。

| 类型 | 实际入口/接续点 | 作用 |
| --- | --- | --- |
| 主 Web 启动 | `templates/index.html` 加载 `static/app/app-storage-location.js`；`static/app/app.js:init()` 调用 `appStorageLocation.init()` | 首次选择、启动阻断、维护页和主页面 startup barrier |
| Web 启动状态哨兵 | `static/js/index.js` 的 `__nekoStorageLocationStartupBarrier` 等待逻辑 | 防止普通首页初始化越过 storage barrier |
| Memory Browser 页面 | `templates/memory_browser.html` 的存储位置卡片与 modal；`static/js/memory_browser.js:initStorageLocationPanel()` | 常驻查看当前根、打开管理、选择目标、预检、重启 |
| Memory Browser 操作按钮 | `openStorageLocationManager()`、`pickStorageTargetDirectory()`、`runStorageLocationPreflight()`、`restartWithStorageLocation()` | 直接进入 `/bootstrap`、`/pick-directory`、`/preflight`、`/restart` 链路 |
| 主 Web 选择/维护 UI | `static/app/app-storage-location.js` 的 select、restart、maintenance polling、completion cleanup | 选择当前根/新根、显示维护、等待新代、清理 retained source |
| Electron 目录/路径入口 | `window.nekoHost.pickDirectory()`、`window.nekoHost.openPath()`；失败才回退后端 `/pick-directory`、`/open-current` | 只提供宿主能力，不执行迁移策略 |
| PC 维护宿主入口 | `src/main/storage-gate.js` 的 `refreshStorageStartupState()`、`enterMaintenanceProtection()`、轮询与 `neko:host:close-window` | 探测后端、保护窗口、允许本地退出；不复制文件 |
| 后端路由入口 | `main_routers/storage_location_router.py` 的 `/bootstrap`、`/status`、`/select`、`/preflight`、`/restart`、`/exit`、retained-source 路由 | 所有策略写入、checkpoint、受控关闭和清理请求的后端边界 |
| launcher 接续入口 | `launcher_core/runtime.py:_resolve_storage_layout_for_launch()`、`_maybe_schedule_storage_restart()` | 下一代启动前执行 pending migration/rebind，并决定 self-spawn/owner relaunch |
| legacy 独立入口 | `utils/cloudsave_runtime/legacy_migration.py` 及 cloudsave bootstrap | 旧版 cloudsave/legacy import；不是用户主动更换运行根的迁移清单 |

因此，用户实际能看到的存储位置入口只有“主 Web 启动选择层”和“Memory Browser 存储位置卡片”；PC 原生层是宿主保护/退出入口，launcher 和 legacy import 是内部接续链，不能合并描述为同一个用户按钮。

### 3.1 纳入本功能的用户能力

- 首次启动选择推荐根、当前根或自定义根；
- Memory Browser 中再次打开存储位置入口；
- 选择当前根并继续当前会话；
- 选择不同根并执行重启迁移；
- 目标目录预检、空间/权限/嵌套/已有内容提示；
- 已提交自定义根离线时显示恢复状态；
- 原路径恢复后的 `rebind_only`；
- 迁移成功后查看当前根和保留源；
- 显式清理保留源；
- Main/Memory Server 启动屏障和存储阻断；
- NEKO-PC 维护期间保护桌面窗口；
- launcher 在新服务初始化前继续 pending migration；
- 失败后保留源和检查点，下一次启动进入恢复。

### 3.2 不纳入本功能的用户能力

- 运行中把已经创建的 `ConfigManager` 热切到另一根；
- 在后端失联时由前端直接修改 policy、root_state 或 migration checkpoint；
- 自动删除迁移源；
- Steam Workshop 外部目录本身的复制；
- 云存档同步协议、Steam Auto-Cloud 冲突解决和云端合并；
- PNGTuber 资源迁移（当前清单未包含）；
- 项目源码目录下的项目级 config/memory 迁移；
- 一般意义的 memory/archive/persona/voice/schema migration；这些是其他功能的迁移，不属于 storage-location 链路。

### 3.3 兼容层但不是独立实现

`utils/storage_migration.py`、`utils/storage_policy.py`、`utils/storage_layout.py`、`utils/storage_location_bootstrap.py` 是兼容导入别名，实际实现位于 `utils/storage/`。维护时必须改实现模块并检查别名导入，不应在兼容文件里重复实现逻辑。

## 4. 根目录、目录所有权和持久化状态

### 4.1 三个运行时概念

| 名称 | 当前含义 |
| --- | --- |
| `anchor_root` | 固定的平台应用数据锚点，保存 policy、migration、root state、cloudsave 和暂存/备份 |
| `selected_root` | policy 已提交的用户运行根 |
| `effective_root` | 当前 ConfigManager 实际使用的运行根；恢复时可能暂时是 anchor |
| `committed_selected_root` | policy 中的稳定选择，即使路径暂时离线也不应静默改写 |
| `reported_current_root` | 恢复 UI 对用户展示的原提交路径 |

推荐 anchor：Windows `%LOCALAPPDATA%/N.E.K.O`、macOS `~/Library/Application Support/N.E.K.O`、Linux `$XDG_DATA_HOME/N.E.K.O` 或 `~/.local/share/N.E.K.O`。

### 4.2 固定在 anchor 的内容

`ConfigManager` 当前把以下内容绑定到 anchor：

```text
<anchor_root>/state/
<anchor_root>/cloudsave/
<anchor_root>/.cloudsave_staging/
<anchor_root>/cloudsave_backups/
```

policy 位于 `<anchor_root>/state/storage_policy.json`，migration checkpoint 位于 `<anchor_root>/state/storage_migration.json`。root state 由 ConfigManager 的 local state 管理，物理路径以该实例解析结果为准。

selected root 改变不会把 cloudsave 或状态控制文件带走。`NEKO_STORAGE_SELECTED_ROOT`、`NEKO_STORAGE_ANCHOR_ROOT`、`NEKO_STORAGE_CLOUDSAVE_ROOT` 只用于 launcher 向当前代及其子进程传递最终布局，不能代替持久化状态。

### 4.3 ConfigManager 创建的目录与迁移清单不是同一件事

`utils/config_manager/storage_roots.py` 当前定义的运行时目录比主动迁移清单更多，包括 `pngtuber` 等目录。目录属性存在，只代表运行时可能读写，不代表该目录已纳入用户主动迁移。

主动迁移清单的唯一当前事实是 `utils/storage/migration.py:61-73`：

```text
config, memory, plugins, live2d, vrm, mmd,
workshop, character_cards, card_faces, jukebox, avatar_tools
```

因此新增目录时必须同时检查 ConfigManager、主动迁移、legacy import、diagnostics、保留源清理和测试；只增加 ConfigManager 属性是不完整功能。

### 4.4 三份状态的职责

#### `storage_policy.json`

记录已经正式生效的 `selected_root`、`anchor_root`、`selection_source`、`cloudsave_strategy`、`first_run_completed` 和更新时间。它不能在用户预览或迁移尚未成功时提前指向目标。

#### `storage_migration.json`

记录待执行或已经完成的主动迁移，包括 source/target、selection source、目标内容确认、backup/retained source、错误和时间字段。当前状态常量：

```text
pending, preflight, copying, verifying, committing,
retaining_source, rollback_required, failed, completed
```

`pending` 至 `rollback_required` 会阻断正常启动；`failed` 配合 root state 的 `deferred_init` 进入恢复界面；`completed` 继续保留，以便完成通知和旧源清理。

#### `root_state`

当前模式包括 `normal`、`bootstrap_importing`、`bootstrap_readonly`、`deferred_init`、`maintenance_readonly`。它是服务是否允许正常写入的启动期写保护真源，不能由 storage status 的派生字段替代。

## 5. 两条经常被混淆的迁移链

### 5.1 legacy bootstrap import

`utils/cloudsave_runtime/legacy_migration.py` 负责旧版本历史目录的启动期导入。它的触发点是 launcher/cloudsave bootstrap，而不是用户在存储位置页点击迁移；它的历史候选根和导入语义不能直接拿来当作主动迁移清单。

典型顺序：

```text
历史 Documents/工作目录候选
  -> 启动期 legacy import
  -> 形成当前 anchor/runtime 的可用数据
  -> 进入首次选择或正常启动
```

### 5.2 用户主动更换运行根

主动迁移由 Web `select/preflight/restart`、router、关闭运行时、launcher 和 `run_pending_storage_migration()` 协作；只复制当前主动清单，不迁移 anchor 固定目录，也不热切换当前 ConfigManager。

两条链都可能出现在升级用户身上，但状态、时序、清单和恢复入口不同。文档和测试必须分开命名。

## 6. 用户实际全流程（当前 0.9.0）

### 6.1 应用启动

1. launcher 清除继承的 `NEKO_STORAGE_*` 环境并重置 ConfigManager cache。
2. launcher 读取 policy、migration checkpoint、root state，解析当前布局。
3. 如果存在 pending migration，先在服务初始化前执行它。
4. launcher 导出最终布局环境变量，执行 cloudsave bootstrap/legacy import。
5. Main Server、Memory Server 根据 selection/migration/recovery blocking reason 决定是否进入 limited mode。
6. Web 通过 `/api/system/status` 和 `/api/storage/location/bootstrap` 判断显示 ready、首次选择、维护或恢复；PC StorageGate 同步探测后端。

### 6.2 首次选择：继续当前会话

1. Web 显示选择层，用户选推荐位置或当前有效根。
2. Electron 环境优先使用 `window.nekoHost.pickDirectory()`；不可用时回退 `/api/storage/location/pick-directory`。
3. Web `POST /api/storage/location/select`。
4. 后端校验路径并在 `_storage_mutation_lock` 内保存 policy、释放 Main/Memory barrier。
5. 返回 `continue_current_session`。
6. Web 关闭选择层，继续当前进程，不建立 migration checkpoint，也不重启。

### 6.3 首次选择/常驻入口：切换到不同路径

1. `select` 校验路径，返回 `restart_required` 和 `restart_mode=migrate_after_shutdown`。
2. Web 展示源、目标、预计数据量、空间、外部盘/同步目录/已有内容等预检信息。
3. 如目标已有受管内容，用户必须显式确认 `confirm_existing_target_content`。
4. Web 调用 `POST /api/storage/location/restart`。

### 6.4 restart 接口提交

普通迁移分支在 `_storage_mutation_lock` 和 root_state transaction 内：

1. 读取 root_state 和已有 migration 的写前快照；
2. 再次校验源/目标和预检阻断项；
3. 写入 pending migration checkpoint；
4. 写入 `root_state.mode=maintenance_readonly` 及 `restart_pending:<target>`；
5. 调用运行时 shutdown callback。

如果 shutdown 尚未被接受而请求取消或调用失败，使用写前快照回滚；如果 shutdown 已被接受，即使等待方随后收到取消，也保留 checkpoint 给 launcher 接力。

### 6.5 恢复路径的 rebind_only

已提交 selected root 暂时不可用时，ConfigManager 可以使用 anchor 建立受限恢复环境，但仍报告原 committed root。用户重新选回该根且路径可用时：

1. `select`/`restart` 返回 `restart_mode=rebind_only`；
2. router 删除旧的迁移 checkpoint并保存 policy；
3. 设置 `maintenance_readonly` 和 `restart_rebind:<root>`；
4. 受控关闭并重启；
5. launcher 重新绑定该根，不复制运行时目录。

这不是一次新的目录迁移，也不是把 anchor fallback 提交成稳定根。

### 6.6 旧服务关闭和桌面保护

Web 进入 maintenance；PC StorageGate 进入维护保护：

- 隐藏 compact/full Chat、subtitle、Agent HUD、Jukebox 等卫星窗口；
- 保存它们的可见性快照；
- 显示 Pet 主窗口和存储遮罩；
- preload 观察遮罩阶段，通过 `neko:storage-location-phase` 通知主进程；
- 后端未 ready 时阻止卫星窗口重新出现。

PC 不复制文件，也不调用后端 migration API 来决定路径；Web 直接调用后端，PC 只提供 `pick-directory`、`open-path`、`close-window` 等宿主能力。

### 6.7 launcher 执行 pending migration

旧服务清理完成后，`launcher_core/runtime.py:_resolve_storage_layout_for_launch()`：

1. 读取 anchor 下的 migration checkpoint；
2. `run_pending_storage_migration()` 进入 preflight；
3. 复制清单中的存在条目；
4. 对目标做结构快照校验；
5. 保存新 policy；
6. 写 root state normal、current/last-known-good/backup/cleanup flag；
7. 写 completed checkpoint 并记录 retained source；
8. 重新解析最终 layout，导出环境变量；
9. 启动 Main、Memory、Agent 等服务。

### 6.8 launcher 接力和新代恢复

`_maybe_schedule_storage_restart()` 在迁移结果 `attempted=True` 或 `restart_rebind:` 时：

1. 发出 `storage_migration_restart`，携带 completed/error/layout/restart_reason/relaunch；
2. 释放单实例所有权；
3. 如果设置了 `NEKO_OWNER_RELAUNCH`，交给 owner；否则走 launcher self-spawn fallback；
4. 新代发 `startup_begin`、`port_plan`、`startup_ready` 或 `startup_failure`；
5. PC backend-runtime 更新当前端口、原始 URL、launch id 和 loading 状态；
6. StorageGate 重新探测 status，ready 后 Web reload，PC 恢复卫星窗口。

0.9.0 的 NEKO-PC 当前没有设置 `NEKO_OWNER_RELAUNCH`，所以实际主路径是 launcher self-spawn，而不是 Electron 主进程主动拉起下一代。

### 6.9 迁移失败

迁移引擎内部的 `StorageMigrationError` 或未预期异常会：

1. 写 failed checkpoint；
2. 记录 error code/message 和 backup/source；
3. 如能确定源根，恢复 policy 到源根；
4. 把 root state 置为 `deferred_init`；
5. 返回 `attempted=True, completed=False`，仍允许 launcher 发 restart event 并拉起恢复代。

这与 launcher 在迁移引擎外围异常时把结果捕获成 `attempted=False` 不同。后者可能导致 `_maybe_schedule_storage_restart()` 没有 restart reason、旧服务退出后没有下一代，是当前需要重点排查的高风险分支。

### 6.10 完成提示和旧源清理

完成 checkpoint 继续保留。Web 完成卡提供：

- 当前生效目录；
- 旧数据保留目录；
- 打开当前/旧目录；
- 清理旧目录；
- 稍后处理。

用户明确清理后，router 重新校验 retained root：

- retained root 等于 anchor 时，只删除主动迁移清单条目，保留 state/cloudsave；
- 独立旧根通过当前实现的目录删除逻辑清理；
- 当前根、目标根、anchor 或不满足边界的路径拒绝清理；
- 清理后更新 migration checkpoint 和 root state 的 cleanup 标记。

当前清理不等于自动移动，不应在迁移成功时隐式执行。

## 8. 当前迁移算法的真实限制

### 8.1 当前有的安全性

- source==target 拒绝；
- source/target 互相嵌套拒绝；
- source 不存在或不可用拒绝；
- 目标已有内容需要显式确认（legacy/recovered 可走已有目标语义）；
- 目标可写性和空间在预检与迁移阶段重新检查；
- source entry 为符号链接时拒绝自动复制；
- 目标同名受管条目先替换，目标无关内容保留；
- `workshop_config.json` 的已知运行根绑定路径在目标副本中重写；
- 迁移失败保留源和 checkpoint，不把目标静默提交为稳定根；
- policy、migration、root_state 写入有锁、worker offload 和取消后等待语义；
- Main/Memory barrier 防止受限状态下继续普通业务写入。

### 8.2 当前没有的能力

- copying 阶段没有逐文件/逐字节 heartbeat，页面进度是阶段映射；
- verification 是类型、文件数量和总字节等结构统计，不是完整哈希证明；
- 没有 `publishing` 状态和通用事务 staging/atomic publish 实现；
- 没有把 `pngtuber` 或所有 ConfigManager 目录自动加入迁移；
- 没有为迁移每一阶段都发送独立 launcher 事件；
- 没有后端失联后由 PC 自动恢复迁移的独立 watcher；
- 当前 UI 没有维护失联终态、强制退出按钮或有界 watchdog。

历史设计中若出现上述能力，必须以当前代码再次确认后才能重新纳入。

## 9. NEKO-PC 当前真实职责

### 9.1 StorageGate

`src/main/storage-gate.js` 当前：

- `deriveStorageGateState()` 识别 `ready`、`maintenance`、`recovery_required`、`selection_required`、`checking`；
- 双 status 都失败时写 `backend_unreachable`；
- 维护态优先轮询 storage status，其他状态优先 system status；
- 非 ready 时阻止卫星动作；
- 维护保护隐藏卫星、显示 Pet，ready 后按快照恢复并可能 reload Pet；
- 1 秒阻断态、3 秒 ready 态轮询；
- 只提供原生目录选择器和打开路径等宿主能力，不复制后端数据。

### 9.2 backend-runtime

`src/main/backend-runtime.js` 当前：

- 维护 backend ownership、runtime lease、spawned/attached/remote 状态；
- 校验 `sourceProcess`、`currentLaunchId`，丢弃旧代事件；
- 接收 `port_plan`/`startup_ready`，更新 active port map 和 original URL；
- 接收 startup failure，结束等待并显示启动失败；
- 对 `storage_migration_processing/completed/failed` 仅更新 loading 文案；
- 对 `storage_migration_restart` 记录事件、清 currentLaunchId、更新 loading，不执行迁移本身；
- 受控退出时优先请求后端认证关闭，等待进程/服务终态，必要时 force stop；
- Electron 退出和后端退出有本地 cleanup、Job holder、runtime lease 保护。

### 9.3 preload 和窗口

- `src/preload/shared/common.js` 暴露 `pickDirectory`、`openPath` 等通用宿主桥；
- `src/preload/bridges/pet-input-region-bridge.js` 观察 Web storage overlay，根据 progress/error/loader/页面视图识别 phase，并发送 `neko:storage-location-phase`；
- overlay 被作为 full-window interactive surface 保护，确保维护页可操作；
- Pet 主窗口的 `neko:host:close-window` 会进入 `requestAppQuit`，但 Web 当前失败分支可能阻断到达该 IPC。

PC 不提供 storage `select/restart/cleanup` bridge；这些决策仍由 Web 直接调用 NEKO 后端，这是跨仓库边界的一部分。

## 10. 当前版本已确认的维护问题

### 10.1 Web maintenance 无限等待

`static/app/app-storage-location.js:1488-1575` 的 `startMaintenancePolling()`：

- `/api/storage/location/status` 失败后尝试 `/api/system/status`；
- 两者都失败时只增加 failure count、显示“等待服务恢复”；
- 每约 1.2 秒继续循环；
- 没有总 deadline、最大失败次数、终态或诊断动作。

### 10.2 后端失联时无法本地关闭

`app-storage-location.js:290-301` 的 `requestHostWindowClose()` 在 maintenance/blocked 状态先 POST `/api/storage/location/exit`。catch 后直接 `return`，因此不会调用同文件已有的 `closeHostWindowOnly()`，也就不会触发 PC 的 `neko:host:close-window`。

这与 PC 的维护保护和 always-on-top 组合后，就形成“页面置顶且无法关闭”。CSS pointer-events 不是直接根因。

### 10.3 PC `backend_unreachable` 没有终态

`storage-gate.js:195-239` 会记录 `backend_unreachable`，但 `826-855` 仍永久 setTimeout 轮询；`updateStorageStartupSnapshot()` 只有 ready 才退出维护保护。因此后端已死时，PC 不会自行提供退出/恢复动作。

### 10.4 launcher 接力外围异常风险

`launcher_core/runtime.py:395-403` 捕获 `run_pending_storage_migration()` 之外的异常时把 migration result 置为 `attempted=False`。`_maybe_schedule_storage_restart():614-638` 只有 `attempted` 或 `restart_rebind` 才建立 restart reason；若外围异常在旧服务退出后出现，可能没有 `storage_migration_restart`、没有下一代 launcher，pending/root_state 仍停在维护态。

迁移引擎内部正常失败返回 `attempted=True, completed=False`，这条路径会继续发送 restart event 并拉起恢复代，不能和外围异常分支混为一谈。

### 10.5 进度固定但不代表数据没有复制

`migration.py:501-523` 在 copying 开始和完成阶段更新 checkpoint，中间同步复制运行时条目；Web 进度是阶段映射。因此大模型/插件目录复制期间百分比不变，当前没有足够信息区分慢迁移和挂死。

### 10.6 端口接力是条件风险

正常 `port_plan`/`startup_ready` 会更新 PC 的 active ports 和 original URL，维护结束时 StorageGate 也可以按 `getOriginalUrl()` reload Pet。只有事件丢失、替代 launcher 未启动或页面 reload 条件未触发时，才可能出现页面仍使用旧 origin；这应通过故障注入验证，不能写成正常路径必然缺陷。

## 13. 排障证据和判定

一次用户故障不能只看页面截图。至少收集：

- `storage_migration.json`：status、source、target、updated_at、error；
- root state：mode、current_root、last_known_good_root、last_migration_result；
- policy：selected_root、selection_source；
- launcher stdout/stderr、退出码、`NEKO_EVENT`；
- PC backend-runtime 的 source process、launch id、port_plan、startup_ready/failure；
- 实际 status 请求的 URL/端口和错误类型；
- 关闭点击后 `/exit` 是否失败、`neko:host:close-window` 是否触发。

判定规则：

| 观察 | 首要方向 |
| --- | --- |
| 无 `storage_migration_restart`，旧服务已退出 | launcher 外围异常、restart reason 未建立、self-spawn 未执行 |
| 有 restart，无 startup_begin | self-spawn、锁、Job、端口或进程托管交接 |
| 有 startup_begin，无 startup_ready | 新代启动屏障、配置布局或端口监听 |
| PC 已 startup_ready，页面仍失败 | origin/reload/旧页面代际问题 |
| checkpoint copying 且更新时间变化 | 慢迁移，不应立即判失败 |
| checkpoint 不再更新且 launcher 消失 | 迁移/接力异常，保留 checkpoint 进入恢复 |

## 15. 维护规则与完成定义

修改存储迁移前必须同时检查：

1. ConfigManager 目录属性；
2. 主动迁移清单和 legacy import 清单；
3. policy、migration、root_state 的状态转换；
4. router 的 mutation lock、worker cancellation 和 rollback；
5. Main/Memory startup barrier；
6. launcher 关闭、接力、端口和 launch id；
7. Web、Memory Browser、PC StorageGate 和 preload phase；
8. retained cleanup 和 diagnostics；
9. 两仓库测试及打包/Steam 手工验证。

完成标准：

- 代码、接口、状态和文档说的是同一套行为；
- 迁移清单和排除清单明确且测试覆盖；
- 失败不会静默提交目标或删除源；

- 下一代 launcher 的所有权、端口和启动证据可追踪；
- 用户在任何维护失败状态都能看到可理解的恢复或退出路径；
