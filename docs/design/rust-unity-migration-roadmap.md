# N.E.K.O Rust 与 Unity 迁移总体路线

> **分阶段架构方案**：截至 2026-10-30，已确认的是先完成 Unity VRM 3D 接管、暂停 Rust 重写、保留必要 Python 环境并维持逻辑功能。Rust Desktop Host、Rust Core 的具体所有权、迁移顺序和 Python worker 形态仍是延后方案，必须在 Unity 验收后重新审批，不因本文存在而自动进入开发。当前 Unity 实施状态见 [Unity VRM 渲染迁移交接](./unity-vrm-migration-handoff)。

## 迁移目标

目标不是单纯替换编程语言，而是在不改变用户可观察逻辑功能的前提下，形成更清晰的运行时所有权：

- Unity 成为 VRM 3D 的正式渲染能力，承担模型、动作、表情、口型和交互表现；
- Rust 的候选长期职责包括桌面宿主、进程生命周期和逐步迁移后的核心运行时能力；
- React 与现有 Web UI 继续负责聊天、设置、插件管理和其他文本密集型界面；
- Python 收缩但不强制消失，继续承载插件及确实依赖 Python 生态的能力；
- 现有聊天、记忆、Agent、插件、用户数据、角色配置和跨平台桌面行为必须有可验证的兼容结果。

Rust 是稳定性、资源和工程治理手段，不是产品目标本身。Unity 3D 是当前产品体验目标，因此不能等待全面 Rust 重写后才开始，也不能用 Rust 原型替代 Unity 的真实完成验收。

## 已确认的实施原则

1. **Unity 先行，Rust 暂停。** 当前阶段只完成 Unity 引入和真实 3D 验收，不同时改写后端或桌面宿主。
2. **Unity 直接接管 VRM。** 正式 VRM 路径不增加功能开关，也不保留 Three-VRM 运行时回退；MMD 继续使用 Three.js，因为它是不同模型格式的现有实现。
3. **Unity 不接管产品状态。** 角色选择、聊天、记忆、Agent、插件、用户数据、音频播放和窗口生命周期仍由 N.E.K.O 与桌面宿主管理。
4. **当前不做无关代码重构。** Unity 阶段只修改完成 3D 接管及验证所必需的入口、桥接、兼容调用和测试。
5. **Python 保留必要运行环境。** 插件和依赖 Python 生态的适配器不因 Rust 迁移被强制重写。
6. **每项状态只有一个权威 owner。** 迁移期可以做只读对比，但不能让 Rust、Python、Electron 和 Unity 同时写入同一业务真相。
7. **没有真实运行证据就不算完成。** Web、Node 或静态合同测试不能替代 Unity 构建、Electron 窗口和实际模型验收。

## 当前双仓边界

当前系统不是两个独立产品，而是业务运行时与桌面原生宿主的组合：

```text
N.E.K.O-PC
Electron 窗口、托盘、快捷键、IPC、多屏、输入区域、更新与进程编排
                         │
                         ▼
N.E.K.O
Main / Memory / Agent 三个主要服务、Agent 内嵌 Plugin listener、Web UI 与业务状态
                         │
              ┌──────────┴──────────┐
              ▼                     ▼
   Unity VRM WebGL 源码路径    其他现有 Avatar 格式
      运行验收待完成           Live2D / MMD / PNGTuber
```

N.E.K.O-PC 不应复制聊天、记忆、角色或插件业务。N.E.K.O 页面也不应自行猜测原生窗口、屏幕和进程状态。跨仓改动必须明确协议生产者、消费者、owner、版本和失败结果。

## 候选目标架构

以下是 Unity 验收后需要重新审批的 Rust 候选边界，不是已经批准的实现合同。具体 crate、WebView、进程和迁移切片必须在 Rust 阶段单独设计和验证：

```text
React 与 Web UI
聊天、设置、历史、插件管理
            │
            ▼
Rust Desktop Host
窗口、托盘、快捷键、权限、更新、进程与 IPC
            │
            ▼
Rust Core
版本化协议、配置、存储、音频与逐步迁移的业务运行时
      │                    │
      ▼                    ▼
Unity Renderer       Python Plugin Worker
VRM 3D 与模型交互     旧插件 SDK、Python 依赖、必要生态适配
```

当前已落地的是准备在既有 Web/Electron 页面中启动 Unity WebGL 的源码路径，但分支尚无正式 WebGL 构建，不能称为正在运行。未来若批准 Rust 宿主，首先应复用验收后的 Avatar 协议和 Unity 构建；是否改变为独立 renderer 进程属于另一项架构决策，不与 Rust 重写默认绑定。

### 能力所有权

| 能力 | 当前 owner | 候选目标 owner | 迁移约束 |
| --- | --- | --- | --- |
| 原生窗口、托盘、快捷键、多屏、输入穿透 | N.E.K.O-PC Electron 主进程 | Rust Desktop Host | 逐平台做行为 parity，不能只用 Web 测试证明 |
| VRM 载入、渲染、VRMA、表情、口型、视线和 SpringBone | Unity WebGL 与 UniVRM 源码路径，运行验收待完成 | Unity Renderer | 不迁入 Rust，不恢复 Three-VRM |
| Live2D、MMD、PNGTuber | 各自现有渲染器 | 保持现状，另案决策 | 不因 VRM Unity 化而删减格式能力 |
| 聊天、设置和插件管理界面 | React 与现有 Web UI | React 与 Web UI | 不把文本密集型 UI 重做进 Unity |
| 服务拉起、实例归属、端口、退出、日志和更新 | Electron 与 Python 启动链 | Rust Desktop Host | 作为 Rust 首批候选，先冻结现有生命周期合同 |
| 配置、存储、协议和音频基础设施 | N.E.K.O Python 与桌面宿主共同承担 | Rust Core | 逐项迁移，兼容现有文件、路径和调用方 |
| 会话、记忆和 Agent | N.E.K.O Python 服务 | Rust Core 的后期阶段 | 语义密度高，必须最后迁移并做只读双跑对比 |
| 插件 SDK 与 Python 依赖 | Python 插件服务 | 独立 Python Plugin Worker | 通过版本化 RPC 接入 Rust，不默认嵌入 CPython |
| 用户数据与角色配置 | N.E.K.O 当前存储层 | Rust Core 最终接管 | 先读旧格式，再迁移；失败必须保持旧数据可恢复 |

## 分阶段路线

### 阶段一 完成 Unity VRM 接管

这是当前唯一活动阶段。范围是让项目自己的 Unity 工程、WebGL 构建和仓库内真实 VRM 在正常 N.E.K.O-PC 启动链中稳定工作。

该阶段的总体门槛是：

- 项目自己的 Unity 工程完成导入、编译、测试和可发行的 WebGL 构建；
- 仓库内真实模型在正常 Electron Pet 启动链中完成透明渲染和核心 Avatar 行为；
- 主桌宠、制卡、预览、取帧与已迁移小游戏完成真实 Unity 冒烟；
- 跨屏、输入、失败恢复、资源释放和桌面打包没有阻断性问题。

完整状态、阻塞和验收表由 [Unity VRM 渲染迁移交接](./unity-vrm-migration-handoff)维护。在该门槛通过前，不启动 Rust 代码迁移。

### 阶段二 冻结迁移合同

Unity 通过验收后，先记录当前系统行为，而不是立即重写。需要冻结：

- REST、WebSocket、ZeroMQ 和 Electron IPC 的请求、事件、错误及关闭语义；
- Main、Memory、Agent 与 Agent 内嵌 Plugin listener 的健康状态、实例身份和启动退出顺序；
- 配置优先级、用户目录、角色数据、记忆数据、插件数据和备份恢复格式；
- Pet、Chat、Subtitle、AgentHUD 的窗口创建、连接和输入行为；
- Avatar 协议、音频时序、模型切换和失败恢复；
- 插件 SDK、依赖安装、权限、生命周期和宿主回调。

合同应由当前实现和可复现运行结果生成，不能根据未来 Rust 设计反向改写现有行为。

### 阶段三 评审并引入 Rust Desktop Host

若阶段二证据支持继续迁移，Rust 的首个生产切片建议优先选择边界清楚、语义密度低且容易做 parity 的桌面生命周期能力：

- 服务发现与拉起；
- 实例身份和健康集判断；
- 端口、进程租约和孤儿进程清理；
- 有序退出、崩溃恢复和日志归属；
- 配置目录、更新和平台权限入口。

这一阶段不迁移聊天、记忆或 Agent 业务。现有 N.E.K.O 服务和 Unity Renderer 仍通过版本化协议被 Rust 宿主管理。每个切片独立验证、独立回退，不建立长期并存的第二套业务实现。

### 阶段四 评审并迁移 Rust Core 基础设施

桌面宿主稳定且新的范围获得批准后，再逐项迁移基础能力：

- 协议类型、校验和错误模型；
- 配置读取、优先级和安全写入；
- 文件存储、缓存、备份和恢复；
- 音频设备、流管线和跨进程传输；
- 不包含业务判断的通用调度和资源生命周期。

每次只迁移一个 owner。Rust 接管写入前，必须先证明它可以读取现有数据、生成等价输出，并在中断后由明确版本恢复；不能让 Python 和 Rust 同时写同一文件或状态。

### 阶段五 评审高语义业务迁移

如果长期目标仍要求迁移会话、记忆和 Agent，它们应最后处理，因为这些模块包含大量隐含语义、时序和跨服务依赖。候选验证方式是只读 shadow 对比：同一输入分别计算结果，由现有 owner 继续对用户和数据生效，Rust 结果仅用于差异分析。

只有当输入、输出、错误、取消、超时、重试和数据副作用均达到合同要求，才切换 owner。切换完成后删除旧实现或降为明确的兼容边界，不能永久保留双写。

### 阶段六 评审 Python 收缩边界

Rust Core 稳定后，再按实际收益决定 Python 收缩范围。已确认必须保留必要 Python 环境，候选保留职责包括：

- 现有 Python 插件 SDK 和第三方插件依赖；
- 确实依赖 Python AI、模型或数据生态且重写收益不足的适配器。

独立 Python worker 是当前优先候选：由 Rust 负责启动、权限、资源限制、版本化 RPC 和失败隔离。是否采用该形态以及是否嵌入 CPython，必须通过插件兼容矩阵和运行基准再决定；默认方案不把 CPython 直接嵌入 Rust 进程，以减少插件崩溃、GIL、动态扩展、原生依赖和运行时路径直接污染系统 owner 的风险。

是否迁移某个 Python 模块取决于稳定性、资源、维护和兼容收益，而不是追求语言纯度。

## 验证和切换规则

每个阶段都必须形成从合同到真实运行的证据链：

1. 单元测试验证纯函数和协议边界；
2. 合同测试让旧实现与新实现消费同一组 fixtures；
3. 集成测试覆盖跨进程、取消、重试、退出和恢复；
4. 真实桌面验证窗口、输入、多屏、音频和 Unity 合成；
5. 性能基线比较启动时间、常驻内存、CPU、GPU、包体和资源释放；
6. 故障注入验证新 owner 失败时不破坏用户数据或留下孤儿进程。

Unity VRM 不采用 Three-VRM 运行时回退。Rust 迁移允许在切换前做只读双跑或离线回放，但正式写入必须只有一个 owner；回退通过精确版本和数据兼容方案完成，不靠隐藏开关长期维持两套实现。

## 消融判断

- **拿掉 Rust**：Unity 3D 仍可先完成，因此 Unity 不应被全面重写阻塞。
- **拿掉 Unity**：Rust 可以改善工程质量，但无法实现当前 3D 产品目标。
- **拿掉 Python**：插件和生态兼容成本会显著上升，且不一定产生用户价值。
- **拿掉 React 与现有 Web UI**：会额外重做聊天、设置和插件管理，扩大范围但不改善 3D 主目标。
- **拿掉行为合同与回放**：无法证明“不改变逻辑功能”，只能依赖主观体验。
- **同时推进 Unity 与 Rust**：渲染、宿主和业务回归会混在一起，故障无法快速归因。

## 主要风险与不确定点

- Unity 的透明合成、多屏 DPI、输入区域、启动时间、常驻内存、GPU 和发行包体仍需真实构建数据。
- 现有 Avatar、窗口和页面行为中可能存在未文档化的 DOM、全局变量和异步时序依赖。
- N.E.K.O-PC 的 Electron 主进程和 N.E.K.O 的高语义服务都包含较大的隐式生命周期，Rust 切片边界需要实测，而不能只按文件拆分。
- 插件实际使用的 Python 包、原生扩展和操作系统能力尚未形成完整兼容矩阵。
- 用户数据迁移必须覆盖旧版本、写入中断、磁盘不足、重复执行和跨版本回退。
- Rust 重写的时间、性能收益和最终包体尚无基准，不应在没有测量前承诺结果。
- Unity、Rust、Python 和第三方依赖的许可证及发行条件需要在正式发布前单独复核。

## 当前不执行的事项

- 不在 Unity 尚未真实验收时启动任何 Rust 原型或生产迁移；
- 不把聊天、设置、插件管理和用户数据迁入 Unity；
- 不为 Unity VRM 增加 feature flag、Three-VRM 回退或第二套渲染实现；
- 不在当前阶段重写插件、记忆、Agent 或桌面窗口；
- 不把 Python 全量删除，也不默认在 Rust 进程内嵌 CPython；
- 不把路线文档当作提交、发布或跨仓改动的授权。
